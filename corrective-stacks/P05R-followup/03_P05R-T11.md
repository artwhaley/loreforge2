# P05R-T11 — Canonical PermissionRule identity and scope integrity

Depends on: T10.
Closes: R05, R08.
Commit prefix: P05R-T11:

## Defects

Hook and helper inspect only 100 rules, then compare polymorphic IDs in memory. Opposite effects for the same logical identity can coexist. No DB uniqueness enforces the identity. Domain resources skip containment validation because a Domain has no row.domain field.

## Touchpoints

src/collections/PermissionRules.ts; src/lib/permissions/rules.ts, capabilities.ts; generated types; src/lib/people/peopleWorkspace.test.ts. T12 will move the production People writer onto this service.

## Required patch

1. Define logical identity as (Domain ID, principal relationTo, principal ID, resource relationTo, resource ID, capability). Declared principalType/resourceType must agree with those relation types. Neither effect nor active status belongs in identity: one row holds the current state.
2. Implement a storage-enforced unique identity despite Payload's polymorphic join tables. Concrete preferred approach: a server-generated, non-customer-editable identity key serialized unambiguously from that tuple, required and uniquely indexed, with hook validation/recomputation on every create/update. Alternatively use verified stored scalar columns plus a compound unique index; document why it is equivalent.
3. Normalize IDs without lossy conversions/collisions. Do not use a concatenation format with ambiguous separators. Reject client attempts to spoof the identity. Ensure every sanctioned write, not just one UI route, goes through the invariant.
4. Make upsertPermissionRule transactional/request-aware and query the exact unique identity. Update an existing row's effect/active state deterministically; do not delete/recreate it or scan the first N candidates.
5. Competing writers must not create duplicates. Use adapter-supported conflict/upsert or bounded whole-transaction retry after uniqueness conflicts. Do not retry inside an already-aborted transaction; no in-memory lock as the sole guarantee.
6. Validate all four principal relation types and all four resource relation types. Global Users/Characters remain global identities; scoped Roles/DomainMemberships/resources must resolve and match the rule Domain. For resourceType Domain compare the resource's OWN ID. Missing scoped rows fail closed.
7. Keep the contract's 24 capabilities including manage_access. Do not implement P07 permission precedence, public behavior, or Share.
8. Plan T14 backfill: deterministic consolidation for equivalent duplicate rows with the same effect/state only when semantics are provably identical; conflicting effects/active states require an explicit resolution, not automatic grant-wins/deny-wins policy. No silent row loss. Document exact duplicate inventory and stop conditions.

## Required regressions

- More than 100 and more than 500 matching rules: a new opposing-effect duplicate cannot coexist with its original.
- Same logical rule update changes the survivor rather than increasing count; repeat requests remain one row.
- Real competing create/update writers leave one current identity; DB constraint rejects an attempted duplicate independently of the hook.
- Every principal/resource kind round-trips; mismatched declared types rejected; Alpha rule pointing to Domain Beta rejected; missing scoped target rejected.
- Identity recomputes correctly on supported identity changes; changed identity cannot collide with another row. Customer-provided identity cannot bypass validation.
- Tests inspect sqlite schema/index metadata and demonstrate constraint behavior; existence of a TypeScript unique flag alone is not evidence.

## Done when

No bounded lookup determines uniqueness, storage rejects duplicates, exact identity writer is ready for T12, scope validation covers Domain resources, and types are current. Real DB conversion remains T14; execution-notes/P05R-T11.md specifies migration requirements.
