# P05R-T12 — Atomic permission controls and durable administrative audit

Depends on: T11.
Closes: R04, R09.
Commit prefix: P05R-T12:

## Defects

Folder Write is create_document + edit_document, but separate delete/create operations commit a half-pair on failure. Role, assignment, membership-add/reactivate, and Folder-rule routes swallow audit-write failures and return normal redirects after committing mutations.

## Touchpoints

src/app/(payload)/api/permission-rules/route.ts, roles/route.ts, role-assignments/route.ts, domain-memberships/route.ts; src/lib/permissions/rules.ts; src/lib/domains/domainAudit.ts; shared transaction helper and existing route tests.

## Required patch

1. Inventory live sanctioned routes/actions for Role definitions, RoleAssignments, DomainMembership changes, and direct Folder PermissionRules. Name the actual production writer for each in the note; do not create a parallel audit system.
2. Authorize using existing server authority and selected Domain. Resolve server actor User and acting Character when applicable; do not accept a form-supplied actor or arbitrary audit context.
3. Each logical submitted admin operation commits its business changes and durable audit together. Join hook-triggered transactions without nested independent commits. Remove catches that log audit failure and then report success.
4. Folder access: use T11's exact identity writer. Inherit deletes the direct rule(s); grant/deny updates the current effect. Read and both Write capabilities submitted by one form save plus audit are one atomic unit. Role default Folder rules use the same invariant; do not implement final effective-access evaluation.
5. An invalid state must reject the save rather than silently updating just the other axis. Identical no-op submissions must not claim a change that never occurred.
6. Role creation/archive (including affected assignments), role batch assignment/removal, membership add/reactivate, and direct permission updates must not outlive failed audit storage. Preserve one coherent membership-removal event when its hook invokes T13's service; avoid duplicate or contradictory events.
7. For a multi-person assignment submission, validate selected people first and treat that submitted batch as one logical transaction; no silent partial success.
8. Use existing form/error-feedback patterns to distinguish rejected/failed saves from success. Preserve submitted choices and do not expose DB internals. Do not redesign tree controls.

## Required regressions

- Inject failure on the second Write capability; exact original Read/Write rows, IDs/effects, RoleAssignments, and audit remain unchanged.
- Inherit from grant and deny removes the complete direct axis; inherited defaults remain untouched. RoleAssignments are byte-for-byte unchanged by permission controls.
- Force audit insert failure for Folder access, Role create/archive, assignment batch/removal, membership add/reactivate. Assert business state rolls back and response carries stable failure feedback.
- Successful operations have correct actor/target/change context and no duplicate removal audit.
- Batch with a valid first selection and invalid/failing later selection commits nothing.
- Direct unauthorized REST/Local API writes remain closed.

## Done when

Audit failure cannot produce successful business changes; Write cannot become a half-pair; all current admin writers use the shared transactional audit seam. Run real route handlers in tests rather than only mocking the audit helper. Record the writer inventory and failure matrix in execution-notes/P05R-T12.md.
