# P05R-T01 — Payload/API Authorization Boundary Hardening

**Branch:** phase-05-remediation · **Commit:** `P05R-T01:` (see commit below)

## Key discovery that shaped the work

Payload 3.88's **Local API defaults every operation to `overrideAccess: true`** (verified in `node_modules/payload/dist/collections/operations/local/{create,find,findByID,…}.js`). Collection `access` config therefore guards the **REST / GraphQL / Payload-Admin** surface — which is exactly the forged-mutation bypass the audit found — while internal server code (actions, services, pages, seed, migrations) continues to run through the Local API seam as before. No internal call-site sweep was required; the audit's "privileged Local API" concern remains tracked as `DEF-AUTH-01/-02` (P07-T02).

## Access changes (B/C)

- Added `access` closures (read/create/update/delete all denied) to `RoleAssignments`, `PermissionRules`, `DocumentCharacterLinks`, `Tags`, `DocumentTags`, `DocumentRelationships`, `Roles`, `DomainMemberships` — mirroring the existing `DocumentProvenanceEvents` pattern. Direct REST/GraphQL/Admin self-grant, self-assign, raw supersedes forge, self-enrollment, and cross-Domain reads are now impossible.
- `Folders`: read stays `() => true` (pre-existing public-read concern tracked `DEF-AUTH-01`/`DEF-PUBLIC-01`); create/update/delete denied — customer Folder CRUD flows only through the guarded `/api/folders` route.
- `Documents`: added `access.update` and `access.readVersions`, both routed through the new shared decision `src/lib/authorization/documentAccess.ts` (`canAccessDocument`, capability `read|update`), so read/update/version decisions cannot drift. Update = read decision (owner/DomainAdmin/active-member or legacy membership) **plus** persisted-lifecycle editability (`canEditDocumentBody`).
- Cross-Domain folder re-file invariant added to `Documents.beforeChange` (defense in depth behind `access.update`): on create and on folder change the hook loads the folder and rejects `folder.domain !== document.domain` (and the legacy-tenant analog) even for `overrideAccess` callers.
- Structural hooks (domain containment, uniqueness, lifecycle) preserved; no client-supplied authority flags introduced.

## Direct attack suite (F) — `src/lib/authorization/accessBoundary.test.ts`

New throwaway-DB integration suite (`npm run test:security`, fresh `sl-civic-archive-security-test.db`, `PAYLOAD_PUSH=true`, auto-cleaned at next run; `*.db` gitignored). Fixture: two Domains (alpha/beta) with owners, a plain attacker User controlling a Character with active membership in alpha only. Four tests:

1. **Local API forged mutations denied, zero state change** — attacker with `overrideAccess: false` + own user context: self-assign beta Role; self-grant `manage_access` PermissionRule; delete another's rule; create beta Role; self-enroll into beta; flip a beta member inactive (cascade trigger); raw supersedes edge; beta Tag; Character link; DocumentTag; Folder create; direct update of beta Document → all throw; before/after counts across 9 collections identical.
2. **Cross-Domain reads denied** — permission-rules/roles/domain-memberships/document-relationships/character-links/document-tags/tags in beta, and beta role-assignments → empty or Forbidden; beta Document `findByID` denied. (Version-list denial asserted REST-side: Payload's Local API version reads do not consult `readVersions` for where-lists in this adapter.)
3. **Cross-Domain re-file rejected at hook level even with authority** (`overrideAccess: true`).
4. **REST level** — Payload's generated REST endpoints (real `@payloadcms/next/routes` handlers, real JWT logins): POST/PATCH/DELETE/GET for role-assignments, permission-rules, roles, tags, document-relationships, documents, domain-memberships, folders, and `GET /api/documents/{id}/versions` all denied (≥400 or empty); owner REST document update still works; **guarded custom routes** still work for owners (role assignment, role creation, Folder Read/Write override, Folder create, membership remove/re-add) and never persist for the attacker (cross-Domain assignment, Folder rule, Folder create, membership add).

Also discovered: querying PermissionRules' polymorphic `resource` field with a plain `{ resource: { equals } }` where throws Drizzle "Not supported" — the app already filters client-side; the test mirrors that.
