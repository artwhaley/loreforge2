# P05R-T02 — Supersession Atomicity, Correction, Provenance, and Invariant Enforcement

Status: complete. Commit: `P05R-T02:` (see git log for hash).

## B. Real DB transaction — evidence

- Adapter: `@payloadcms/db-sqlite` 3.88.0 with the libsql local (`file:`) client.
- Payload wiring discovered during execution: the SQLite adapter only wires a real
  `beginTransaction` when `transactionOptions` is configured; otherwise
  `payload.db.beginTransaction` is `defaultBeginTransaction()` resolving `null`,
  and every multi-operation flow is a sequence of auto-committing statements.
  Probe evidence: without `transactionOptions`, `beginTransaction` returned
  `null`.
- Fix (payload.config.ts): `transactionOptions: { behavior: 'immediate' }`,
  `busyTimeout: 5000`, `wal: true`. `immediate` takes the write lock at BEGIN;
  `busyTimeout` makes concurrent writers wait instead of failing with
  SQLITE_BUSY; WAL keeps readers unblocked.
- Probe results against a throwaway DB (`PAYLOAD_PUSH=true`):
  - writes joined via `req: { transactionID }` persist after `commitTransaction`;
  - writes are discarded after `rollbackTransaction` (no row, no provenance);
  - a Document create inside an open transaction succeeds even though its
    `beforeChange` hook performs its own `req.payload.find` read.
- Adapter limitation discovered (evidence for the concurrency design): the libsql
  local client is single-connection, so two overlapping transactions cannot run
  — a second `beginTransaction` while one is open is refused with
  `SQLITE_BUSY: database is locked`. The fork guarantee therefore rests on the
  in-transaction invariant re-read plus the DB unique indexes, and the
  concurrency regression (H) is asserted as consecutive attempts: the first
  wins; the loser fails cleanly with the surfaced invariant error and leaves no
  edge, lock, or provenance. Launched truly in parallel, the loser would fail
  with SQLITE_BUSY instead — also a clean surfaced failure, never a fork.

## A. Supersede-create ordering (archive.ts)

`createDocumentFromEditorAction` previously created the successor Document
first and called `addDocumentRelationship` afterwards: a non-admin member could
orphan a filed near-duplicate when relationship authorization failed. Now, for a
superseding create:

1. predecessor must exist in the same Domain (unchanged);
2. **eligibility preflight** — `canSupersedeDocument(lifecycle)`; see ruling below;
3. predecessor must not already have a successor (unchanged);
4. the interim decision is required **before any create** (`superseding &&
   interim !== true` returns `authorization`);
5. `runInTransaction` wraps successor create → `addDocumentRelationship`
   (joins the same transaction) → `created`/`filed` provenance events;
6. commit. Any failure rolls back all of it — no orphaned successor, no stale
   lock, no stray provenance.

`addDocumentRelationship` itself is now self-atomic: standalone callers (the
sanctioned `/api/document-relationships` route, tests) get their own real
transaction; the archive flow passes its `transactionID` to join.

## Eligibility ruling (A / G)

Draft and Pending-Review records are **never** superseded — Drafts are edited
and Pending-Review records are workflow objects (`ALLOWED` map in
`lifecycle.ts`: `pending_review -> filed|draft` only). Only `filed` and
already-`locked` records may gain a successor (`canSupersedeDocument` in
`src/lib/documents/lifecycle.ts`). UI surfaces (RecordsExplorer toolbar +
context menu, Document page) only offer Supersede for eligible records, and the
server enforces regardless of UI.

`supersedesLock` in `Documents.beforeChange` is narrowed: it permits only
`filed -> locked` and `locked -> locked`; `draft -> locked` and
`pending_review -> locked` throw.

## C. Collection-boundary invariants (DocumentRelationships)

The `beforeChange` hook now rejects, in addition to the pre-existing
self-link / kind / Domain-containment checks:

- a second successor (target already superseded by another edge);
- a second predecessor (source already superseding another edge);
- cycles (same `assertNoSupersedesCycle` walk used by the service, shared from
  `src/lib/documents/relationshipInvariants.ts`; `excludeEdgeId` on update).

Defense in depth: the service preflights with good error messages; the hook
guards direct Local API writes; DB unique indexes guard the storage layer.

## D. Database uniqueness

Two additive unique compound indexes on `document-relationships`:
`{ source, kind }` and `{ target, kind }` (kind vocabulary is a single value,
so this is equivalent to the partial unique indexes the ticket envisioned).
Applied by schema push (`PAYLOAD_PUSH` defaults true outside the `dev` script;
the `npm test`/`npm run test:security` runs push fresh test DBs). The existing
dev database receives the additive index on the next boot with push enabled —
no fixture reset was needed.

## F. Provenance semantics (option a chosen)

On edge creation the **predecessor's own timeline** now shows:

- `locked` (context `{ reason: 'superseded', supersedingDocumentId }`) only when
  the lock is newly applied;
- `superseded` (context `{ supersedingDocumentId }`) — always, so older records
  read as "was superseded by a newer record" (`describeProvenanceEvent` is
  direction-aware via context);
- `relationship_added`.

The successor records the counterpart `superseded` event ("superseded an older
record") plus `relationship_added` on the predecessor. Regression-asserted in
`supersession.test.ts` ("predecessor timeline shows superseded-by").

## E. Audited correction

`removeDocumentRelationship` (alias `correctSupersession`) is transactional:
deletes the edge; if no superseding successor remains for the predecessor, its
lifecycle is restored `locked -> filed` through the sanctioned lifecycle rule
(`interimWorkflowAuthorized` context — the actor was already authorized), never
a raw flag; provenance (`unlocked`, `relationship_removed`) is recorded on both
endpoints. Re-adding a successor re-locks. Removing a non-existent edge fails
cleanly.
