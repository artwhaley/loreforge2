## D. Polymorphic PermissionRule validation

`PermissionRules.beforeChange` now rejects: principalType/resourceType vs

## E. Duplicate-rule prevention

Logical identity = Domain + principalType + principal + resourceType +
resource + capability. The collection hook is **read-only** and aborts any
write that would duplicate an identity. Deterministic effect changes go
through the new `upsertPermissionRule` service
(`src/lib/permissions/rules.ts`): existing identity → in-place update;
otherwise create. Two constraints, both verified:

- SQLite stores polymorphic relations in the `permission_rules_rels` join
  table (confirmed by table inspection: no `principal_id`/`resource_id`
  columns on the main table), so no column unique index can express the
  identity.
- Hook-level writes are impossible on this adapter with real per-operation
  transactions enabled (P05R-T02 B): a `req.payload.update` inside
  `beforeChange` fails with `SQLITE_BUSY` (single-connection libsql client
  cannot begin a second transaction while the outer op's transaction is
  open). Evidence recorded from the first implementation attempt.

## J. Prepared-by working rule (CC-2026-09-03-05)

Enforcement and architecture note:

- `Documents.beforeChange`: creating WITHOUT an acting Character
  (`allowUserCreate` context, no `preparedByCharacterId`) requires the actor
  to be the Domain Owner or an active Domain Admin (interim authorization);
  ordinary members are rejected with an explicit error.
- The non-removable credit is applied by the application actions via
  `ensurePreparedBy` **after** the create commits. It can no longer run in an
  `afterChange` hook: with real per-operation transactions, hook-inner
  payload calls neither see the just-created row (uncommitted) nor begin
  their own nested transaction (SQLITE_BUSY). The
  `preparedByCharacterId` context flag still marks the create as
  Character-authored for the gate and audit.
- Action-level UX: members without an acting Character are short-circuited
  with the `character` error and updated copy ("choose an acting
  Character — members must create through one").
- Tests: owner-without-Character creates with no credit; member-without-
  Character rejected; member-with-Character + `ensurePreparedBy` carries a
  credit that cannot be removed. `ensurePreparedBy`'s active-membership check
  unchanged (BigPickle's unclaimed-Character template concern remains a P06
  question).
